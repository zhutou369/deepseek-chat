在构建基于大模型的智能应用时，除了模型的性能和效果，其API的并发处理能力是决定应用用户体验和可扩展性的关键因素。特别是当应用部署在如火山引擎这样的弹性云平台上，面对高并发场景时，后端AI服务的响应能力至关重要。本文将指导你如何评测 DeepSeek API 的并发能力，以确保其能扛住来自火山引擎等平台的高压流量。

我们将通过一个实际的并发压力测试来模拟火山引擎应用可能产生的请求负载，并分析 DeepSeek API 在高并发下的表现。

## 1. DeepSeek API 基础配置

在进行并发测试之前，首先需要获取 DeepSeek API 的访问凭证并了解其基本调用方式。

### 1.1 获取 API Key

访问 [chat.deepseek.com](https://chat.deepseek.com) 并登录你的账户。在用户中心的“API Keys”页面，你可以生成或管理你的 DeepSeek API Key。务必妥善保管你的 Key，不要将其硬编码到公开的代码库中。

### 1.2 DeepSeek API 接口概述

DeepSeek 提供了标准的 RESTful API 接口，其兼容 OpenAI API 协议，因此许多现有的工具和 SDK 都能直接复用。主要的文本生成接口是 `/v1/chat/completions`。

以下是一个基本的 DeepSeek API 调用示例（Python 版），用于验证 API 可用性：

```python
import httpx
import asyncio
import os

# 从环境变量获取 DeepSeek API Key
DEEPSEEK_API_KEY = os.getenv("DEEPSEEK_API_KEY")
if not DEEPSEEK_API_KEY:
    raise ValueError("请设置 DEEPSEEK_API_KEY 环境变量")

DEEPSEEK_API_BASE = "https://api.deepseek.com/v1"

async def call_deepseek_api(prompt: str):
    headers = {
        "Content-Type": "application/json",
        "Authorization": f"Bearer {DEEPSEEK_API_KEY}"
    }
    payload = {
        "model": "deepseek-chat",  # 评测时建议选用一种固定模型
        "messages": [
            {"role": "user", "content": prompt}
        ],
        "stream": False # 并发测试通常不使用流式传输
    }

    async with httpx.AsyncClient(base_url=DEEPSEEK_API_BASE, timeout=30) as client:
        try:
            response = await client.post("/chat/completions", headers=headers, json=payload)
            response.raise_for_status() # 检查 HTTP 错误
            result = response.json()
            # print(f"API Response: {result['choices'][0]['message']['content']}")
            return result['choices'][0]['message']['content']
        except httpx.HTTPStatusError as e:
            print(f"HTTP error occurred: {e.response.status_code} - {e.response.text}")
            return None
        except httpx.RequestError as e:
            print(f"An error occurred while requesting {e.request.url!r}: {e}")
            return None

if __name__ == "__main__":
    test_prompt = "请用一句话概括人工智能的发展趋势。"
    # 在实际运行前，确保 DEEPSEEK_API_KEY 已配置为环境变量
    # 例如：export DEEPSEEK_API_KEY="YOUR_DEEPSEEK_API_KEY"
    print("正在执行 DeepSeek API 测试...")
    response_content = asyncio.run(call_deepseek_api(test_prompt))
    if response_content:
        print(f"DeepSeek API 返回: {response_content[:100]}...") # 打印前100字
    else:
        print("DeepSeek API 调用失败。")

```
这份代码片段展示了如何使用 `httpx` 库进行异步 API 调用。在火山引擎的函数计算或容器服务中，你可以将类似逻辑封装为服务，用于处理用户请求。

## 2. 设计并发评测场景

为了有效评估 DeepSeek API 的并发能力，我们需要设计一个合理的评测场景，包括请求负载、请求内容和关键性能指标。

### 2.1 模拟请求负载

*   **并发用户数 (Concurrency)**：模拟同时有多少用户或服务实例在请求 DeepSeek API。
*   **请求总数 (Total Requests)**：在测试期间发送的总请求数量。
*   **持续时间 (Duration)**：测试将持续多长时间。
*   **请求间隔 (Ramp-up)**：请求从零逐渐增加到最大并发数的速度。

### 2.2 确定测试内容

为了避免因为复杂Prompt导致模型响应时间过长，影响对并发能力的纯粹测试，建议使用短小、明确、且能快速得到响应的Prompt。

**示例 Prompt**: "请用一句话描述夏天最适合做什么？"

这样的Prompt可以确保 DeepSeek 模型能在毫秒级到秒级内完成推理，从而更准确地反映API接口和底层网络的并发处理能力。

### 2.3 关键性能指标 (KPIs)

我们将关注以下指标：

*   **吞吐量 (Throughput)**：每秒完成的请求数 (RPS - Requests Per Second)。
*   **响应时间 (Response Time)**：每个请求从发送到接收完整响应的时长。通常关注平均值 (Average)、中位数 (P50)、95百分位 (P95) 和 99百分位 (P99)。
*   **错误率 (Error Rate)**：请求失败（如HTTP 5xx 错误、超时错误）的比例。

## 3. 实现高并发压力测试

我们将使用 Python 的 `asyncio` 结合 `httpx` 来编写一个简单的并发测试脚本。这种方法足够灵活，可以在本地环境或火山引擎的虚拟机、容器服务中运行。

### 3.1 编写并发测试脚本

创建一个 `stress_test.py` 文件：

```python
import httpx
import asyncio
import time
import os
from collections import defaultdict

# 配置 DeepSeek API
DEEPSEEK_API_KEY = os.getenv("DEEPSEEK_API_KEY")
DEEPSEEK_API_BASE = "https://api.deepseek.com/v1"
if not DEEPSEEK_API_KEY:
    raise ValueError("请设置 DEEPSEEK_API_KEY 环境变量")

# 测试参数
CONCURRENCY = 20        # 并发数
TOTAL_REQUESTS = 100    # 总请求数
PROMPT = "请用一句话描述夏天最适合做什么？"
MODEL_NAME = "deepseek-chat"
TIMEOUT = 30 # 秒

# 存储结果
response_times = []
success_count = 0
fail_count = 0
rate_limit_count = 0

async def send_request(session: httpx.AsyncClient, prompt: str, request_id: int):
    global success_count, fail_count, rate_limit_count
    headers = {
        "Content-Type": "application/json",
        "Authorization": f"Bearer {DEEPSEEK_API_KEY}"
    }
    payload = {
        "model": MODEL_NAME,
        "messages": [
            {"role": "user", "content": prompt}
        ],
        "stream": False
    }

    start_time = time.monotonic()
    try:
        response = await session.post("/chat/completions", headers=headers, json=payload)
        end_time = time.monotonic()
        duration = (end_time - start_time) * 1000 # 转换为毫秒
        response_times.append(duration)

        if response.status_code == 200:
            success_count += 1
            # print(f"Request {request_id} successful, duration: {duration:.2f}ms")
        elif response.status_code == 429: # DeepSeek 速率限制错误码
            rate_limit_count += 1
            fail_count += 1
            # print(f"Request {request_id} failed: Rate limit (429)")
        else:
            fail_count += 1
            # print(f"Request {request_id} failed: HTTP {response.status_code} - {response.text}")

    except httpx.RequestError as e:
        end_time = time.monotonic()
        duration = (end_time - start_time) * 1000 # 记录超时或连接错误的持续时间
        response_times.append(duration)
        fail_count += 1
        # print(f"Request {request_id} failed: {e}")
    except asyncio.TimeoutError:
        end_time = time.monotonic()
        duration = (end_time - start_time) * 1000 # 记录超时或连接错误的持续时间
        response_times.append(duration)
        fail_count += 1
        # print(f"Request {request_id} failed: Timeout")

async def run_stress_test():
    global response_times, success_count, fail_count, rate_limit_count
    
    response_times = []
    success_count = 0
    fail_count = 0
    rate_limit_count = 0

    print(f"--- DeepSeek API 并发压力测试 ---")
    print(f"并发数: {CONCURRENCY}")
    print(f"总请求数: {TOTAL_REQUESTS}")
    print(f"Prompt: '{PROMPT}'")
    print(f"模型: {MODEL_NAME}")
    print(f"API Base: {DEEPSEEK_API_BASE}")
    print(f"超时时间: {TIMEOUT}s")
    print("-" * 30)

    start_global_time = time.monotonic()

    async with httpx.AsyncClient(base_url=DEEPSEEK_API_BASE, timeout=TIMEOUT) as client:
        # 创建一个信号量来控制并发数
        semaphore = asyncio.Semaphore(CONCURRENCY)

        async def worker(request_id):
            async with semaphore:
                await send_request(client, PROMPT, request_id)

        tasks = [worker(i) for i in range(TOTAL_REQUESTS)]
        await asyncio.gather(*tasks)

    end_global_time = time.monotonic()
    total_duration = end_global_time - start_global_time

    print("\n--- 测试结果 ---")
    print(f"总耗时: {total_duration:.2f} 秒")
    print(f"成功请求: {success_count}")
    print(f"失败请求: {fail_count}")
    print(f"其中速率限制错误 (429): {rate_limit_count}")
    print(f"总请求数: {success_count + fail_count}")

    if success_count > 0:
        avg_rt = sum(response_times) / len(response_times)
        response_times.sort()
        p50_rt = response_times[int(len(response_times) * 0.5)]
        p95_rt = response_times[int(len(response_times) * 0.95)]
        p99_rt = response_times[int(len(response_times) * 0.99)]

        print(f"平均响应时间: {avg_rt:.2f} 毫秒")
        print(f"P50 响应时间: {p50_rt:.2f} 毫秒 (50% 的请求在此时间内完成)")
        print(f"P95 响应时间: {p95_rt:.2f} 毫秒 (95% 的请求在此时间内完成)")
        print(f"P99 响应时间: {p99_rt:.2f} 毫秒 (99% 的请求在此时间内完成)")
        print(f"吞吐量 (RPS): {(success_count + fail_count) / total_duration:.2f}")
    else:
        print("无成功请求，无法计算响应时间统计。")

if __name__ == "__main__":
    # 在运行前，确保 DeepSeek API Key 已配置
    # export DEEPSEEK_API_KEY="YOUR_ACTUAL_DEEPSEEK_API_KEY"
    asyncio.run(run_stress_test())

```

## 4. 结果分析与优化建议

根据测试结果，我们可以评估 DeepSeek API 的并发表现，并结合火山引擎的部署特性，提出优化建议。

### 4.1 评估 DeepSeek API 并发能力

*   **高吞吐量与低延迟**: 如果你的成功请求数接近总请求数，且 P95/P99 响应时间都在可接受范围内（例如，对于实时交互应用，数百毫秒内通常视为优秀），说明 DeepSeek API 在当前并发设置下表现良好。
*   **速率限制 (HTTP 429)**: 如果你看到大量的 429 错误，这表明你已经触及了 DeepSeek API 的速率限制。
    *   **解决方案**:
        *   **增加并发数但不过载**: 适当调高 `CONCURRENCY` 再次测试，观察 429 错误的出现时机。
        *   **指数退避与重试**: 在你的应用逻辑中实现指数退避和重试机制，当遇到 429 错误时，等待一段时间后再次尝试。
        *   **负载均衡与限流**: 在火山引擎应用侧，可以考虑使用负载均衡器对DeepSeek API的请求进行分发，并实现客户端限流，避免瞬时流量过大。
        *   **申请更高配额**: 如果业务需求确实需要更高的并发，可以联系 DeepSeek 官方申请更高的 API 请求配额。
*   **其他错误**: 如果出现其他 HTTP 错误 (如 5xx) 或网络超时，可能是 API 服务端问题，或你的网络连接不稳定。

### 4.2 火山引擎侧的集成与优化

当将 DeepSeek API 集成到火山引擎的应用程序时，除了关注 API 本身的性能，还需考虑平台特性：

*   **函数计算 (Function Compute)**：
    *   **弹性伸缩**: 函数计算可以根据流量自动伸缩实例。确保你的函数配置了足够的内存和 CPU，以便处理并发请求并在等待 DeepSeek 响应时不会成为瓶颈。
    *   **异步调用**: 对于非实时性要求高的任务，可以考虑将 DeepSeek API 调用放入消息队列（如火山引擎消息队列 MQ）中，通过异步函数进行处理，从而解耦并提高主服务的响应速度。
*   **容器服务 (VKE/ACK)**：
    *   **服务网格**: 利用服务网格（如 Istio）进行请求的路由、重试、熔断，以增强对 DeepSeek API 调用的韧性。
    *   **连接池**: 在应用程序中使用 HTTP 客户端连接池（如 `httpx.AsyncClient` 默认的连接池管理），可以复用 TCP 连接，减少连接建立开销，提高效率。
*   **网络延迟**: DeepSeek API 服务器可能距离你的火山引擎部署区域有一定距离，导致网络延迟。尽量选择地理位置相近的区域部署应用。
*   **缓存策略**: 对于重复性高、变化不大的 DeepSeek API 请求，可以考虑在火山引擎应用侧实现缓存机制（如使用 Redis），减少对 DeepSeek API 的实际调用次数。

> **延伸**: 不同的 Prompt 设计会对 DeepSeek API 的响应时间产生显著影响。在实际应用中，建议参考 `/posts/deepseek-chat-scenario-library/` 设计你的提示词库。
